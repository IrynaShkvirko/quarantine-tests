**Context.** Every M1–M4 task reads or writes these tables. Building the full §10 schema once, with the right keys and indexes, avoids a migration per feature task.

**Implementation**

1. SQLAlchemy models in `backend/app/db/models/`, one module per area (`repos.py`, `tests.py`, `runs.py`, `quarantine.py`, `jira.py`, `stats.py`), for every table and column in §10. Use `BIGINT GENERATED ALWAYS AS IDENTITY` primary keys, `timestamptz` everywhere, and Postgres enums only where the set is fixed (`outcome`, `evidence`, `job_kind`, `event`); free text with a `CHECK` elsewhere, so new states don't need an enum migration.
2. Keys and constraints:
   - `repositories.full_name` unique; `tests (repository_id, test_key)` unique; `ci_runs (repository_id, ci_system, run_id)` unique; `failure_signatures.fingerprint` unique; `jira_issues.issue_key` unique; `daily_test_stats (day, test_id)` primary key.
   - Every foreign key from a repository's data chain uses `ON DELETE CASCADE` (repositories → tests, ci\_runs, raw\_uploads, bot\_pull\_requests; tests → executions, flaky\_events, quarantine\_records, manual\_skips, daily\_test\_stats; and onward), so deleting a demo repository removes all its rows (§15).
   - `raw_uploads` gets the idempotency key columns from M0-08 with a unique index.
3. Partitioning: `test_executions` is `PARTITION BY RANGE (executed_at)`, monthly. The migration creates the parent, a default partition and partitions for the current and next 2 months. A SQL function `fq_ensure_partitions(months_ahead int)` creates missing ones; the retention job (M6-04) calls it. Primary key is `(id, executed_at)` because Postgres requires the partition key in it.
4. Indexes for the hot queries (write each query in a comment next to its index):
   - flaky detection: `test_executions (test_id, executed_at)` and an index on `ci_runs (repository_id, commit_sha, environment)` (§10);
   - inventory: `tests (repository_id, last_seen_at)`, `tests (team_id, state)`;
   - lifecycle: `quarantine_records (test_id) WHERE exited_at IS NULL`, `jira_issues (status, due_date)`.
5. Alembic revision `0002_schema_v1` (autogenerate, then hand-check). Also revision `0003_procrastinate` applying Procrastinate's schema SQL if M0-06 didn't.
6. Grafana role: `GRANT USAGE` and `SELECT` on a `reporting` schema only. Views come in later tasks; create the empty schema now so the grant is in place.
7. `docs/db.md`: generated table list (from the models) and the partition/retention rules.

**Out of scope.** SQL views for Grafana (each dashboard task adds its own), retention job (M6-04), repository code beyond models.

**Acceptance criteria**

- [ ] `alembic upgrade head` on an empty DB creates every §10 table and column; `alembic downgrade base` removes them.
- [ ] A test inserts a demo repository with a full chain (test, run, execution, quarantine record, Jira issue) and deleting the repository leaves zero rows in every table.
- [ ] `fq_ensure_partitions(3)` is idempotent and creates the missing months.
- [ ] Inserting a duplicate `(repository_id, test_key)` or ingestion idempotency key fails with a unique violation.
- [ ] A test compares model metadata against §10's table and column list (kept as a fixture) so drift is caught.

**Tests.** Integration tests for migrations, cascades, partitions and unique constraints; `EXPLAIN` checks that the detection query uses its index on a few thousand seeded rows.
