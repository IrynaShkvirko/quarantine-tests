**Context.** Tasks live in GitHub Issues with milestones and a Project board. All 76 tasks should get there by script, not by hand, and the script must be safe to run again as the plan changes.

**Implementation**

1. `scripts/github/import_tasks.py` (Python, uses the `gh` CLI through `subprocess`, so auth is whatever `gh auth login` set up). Inputs:
   - `--tasks tasks.csv`: the Tasks tab of the Implementation Plan sheet exported as CSV (ID, Milestone, Task, Component, Est. days, Depends on, Status, Doc §, Scope, Acceptance criteria).
   - `--bodies docs/tasks/`: optional folder of Markdown bodies, one file per task (`M0-01.md`), produced by exporting a breakdown doc like this one and splitting on `## M0-` headings. When a body file exists it is used; otherwise the body is built from the CSV's Scope and Acceptance criteria columns.
   - `--repo owner/name`, `--dry-run`.
2. What it creates or updates:
   - **Milestones** M0 to M7 with the milestone names as titles and descriptions from the Milestones tab.
   - **Labels:** `milestone:M0` to `milestone:M7`, one per component (`infra`, `backend`, `ci`, `plugins`, `integrations`, `grafana`, `demo`, `docs`, `ui`), `spike`, `later`. Fixed colours per group.
   - **Issues:** title `[M0-01] Repo skeleton and tooling`; body ends with a hidden marker `<!-- fq-task-id: M0-01 -->`.
   - **Dependencies:** a "Depends on" list in the body linking the issue numbers (resolved after all issues exist, in a second pass). If the repo has GitHub's native issue dependencies ("blocked by") available, also set them; if the API refuses, keep the body list only.
   - **Project board:** a Project (v2) named "Flaky Test Quarantine" with a Status field (To do / In progress / Review / Done) and an Estimate number field; every issue added with its estimate.
3. Idempotency: find existing issues by the `fq-task-id` marker (or the `[M0-01]` title prefix) (`gh issue list --search`), update title/body/labels/milestone if they changed, never create a duplicate. Tasks with status `Later` get the `later` label and stay open but unscheduled.
4. `--dry-run` prints a table of create/update/skip actions and makes no API calls that write.
5. `docs/tasks/README.md` explains the export → split → import flow.

**Out of scope.** Syncing status back from GitHub to the sheet. From this point GitHub is the source of truth for status.

**Acceptance criteria**

- [ ] Running the script on the 76-task CSV creates 8 milestones and all labels, adopts the 13 M0 issues already created by `scripts/github/create_m0_issues.sh` (matched by the `fq-task-id` marker) and creates the other 63, with every issue on the board.
- [ ] Running it a second time creates nothing and reports "no changes".
- [ ] Changing one task's title in the CSV and re-running updates only that issue.
- [ ] Every issue's "Depends on" links point to the right issue numbers.

**Tests.** Unit tests for CSV parsing, body building, marker matching and dependency resolution, with `gh` calls behind an interface replaced by a fake.
